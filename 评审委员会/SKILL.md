# 评审委员会

> 解决的是「自己写、自己看、自己过」最容易出现的问题：**单一视角盲区**。
> 你是个人开发者，没有团队互审，于是用一个技能包模拟五个角色的把关。
>
> **本包的方法论融合自 GitHub 项目 `garrytan/gstack`（约 132k stars，2026-09 核实）的
> 多角色评审机制（plan-eng-review / plan-ceo-review / design-review / qa / retro），
> 并针对「个人学生开发者、无协作者、无组织政治、无部署协调需求」做了大幅精简。**

---

## 五个视角的分工（避免重复——这是 gstack 的核心设计）

五个视角**各有禁区**，绝不能互相越界，否则评审会重复且互相打架。

| 视角 | 把关什么 | **不负责什么** |
|---|---|---|
| 工程 | 架构、代码质量、测试覆盖、复杂度、实现正确性 | 不管界面好不好看 |
| 产品 | 价值、范围、可逆性、6 个月后还成立吗 | 不管具体怎么实现 |
| 设计 | 可学习性、信任感、空状态、响应式、减法 | 不管代码结构 |
| QA | 真实行为验证、回归、边界、证据 | 不管设计意图 |
| 复盘 | 过程度量：是否碎片化、是否总在修 bug | 不管单次改动对错 |

> 融合说明：gstack 原版把 23 个角色拆得很细（如 eng-review、ceo-review、design-review、
> qa、retro、ops、legal 等）。我合并为 5 个最贴合个人开发者的视角，砍掉了 ops（部署协调）、
> legal（合规）、people（人事）等对个人开发者无意义的角色，详见各 references 文件内的「本地化裁剪」标注。

## 统一评审规则（最重要，必须照做）

### 1. 严重程度四级

| 级别 | 含义 | 处理方式 |
|---|---|---|
| **阻断** | 有 bug / 安全漏洞 / 丢数据 / 违背明确需求 | 不改不通过 |
| **重要** | 设计问题 / 性能不行 / 可维护性差 | 应该改，不改要说明理由 |
| **建议** | 命名、风格、更优雅的写法 | 可改可不改，作者决定 |
| **疑问** | 看不懂，可能是我没理解 | 请作者解释，不是要求改 |

**一份全是「阻断」的评审等于没有评审；一份全是「建议」等于放水。** 必须混合分级。

### 2. 置信度 1-10（每条意见都要打分）

- **9-10**：亲眼见证据，确定无疑
- **6-8**：高概率正确，逻辑清晰
- **3-5**：有迹象但不确定，需要作者确认
- **1-2**：纯猜测，仅供参考

> 融合自 gstack 的 confidence 机制。目的是**逼评审者区分「我确定」和「我觉得」**，
> 避免 AI 把猜测当成确定结论吓到人。

### 3. pre-emit verification gate（证据门）——杜绝幻觉式评审

> 这是本包与「随便聊聊」最根本的分界。AI 评审最大的风险是**编出看似合理的 file:line 来显得专业**。

**硬性规则：**

- 每条 finding **必须引用具体的 `file:line` 或可验证的事实**（实测输出、报错、git 记录）。
- **引用不出来的意见，必须降低置信度（打 1-3 分）并放入「附录·未验证」区，绝不允许当作确定结论输出。**
- 引用了 `file:line` 但读者核对后不存在的，整条作废并自罚标注。

**反例（禁止）：** 
> ❌ “第 42 行的循环可能导致性能问题” —— 但根本没看过第 42 行。

**正例：** 
> ✅ [重要] [置信度 8/10] 定时任务未做去重，并发启动会重复执行 — 证据(`巡检脚本.py:131` 的 `while True` 无锁无单例) — 建议加文件锁或利用系统 cron。

### 4. 输出模板

```
[严重程度] [置信度 n/10] 问题简述 — 证据(file:line 或可验证事实) — 建议
```

每个视角输出结束后，统一附一个：

```
## 附录·未验证（置信度 ≤3，无直接证据，仅供作者参考）
- [疑问][置信度 2/10] 我不确定这里……（请作者确认）
```

## 视角选择指引（不是每次都要五视角全开）

按任务路由，省 token 也省噪音：

| 触发场景 | 开哪些视角 |
|---|---|
| 改代码 / 提 PR / 提交前自查 | 工程 + QA |
| 做新功能 / 竞赛方案 / 课程项目 | 产品 + 工程 + 设计 |
| 出 UI / 小程序页面 / 官网改版 | 设计 + QA |
| 项目告一段落 / 周复盘 / 期末总结 | 复盘 |
| 重大决策 / 架构选型 / 技术栈选择 | 全开（5 视角） |

> 当 team-lead 分发评审任务时，也可直接指定视角。没有明确指定时，按上表路由。

## 与其他技能的关系

- `工程方法论工具箱` 管「**怎么做才可靠**」（调试 / TDD / 完成前验证 / 代码审查），本包管「**多角度把关**」——视角更广、但不替代方法论的深度执行。两者互补：本包的「工程视角」发现问题后，复杂修复应回到方法论工具箱走 TDD/验证。
- 具体领域审查走对应工具箱：安全审查 → `安全审查工具箱`；文档质量 → `文档工具箱`。
- 本包是**角色化把关层**，方法论工具箱是**执行层纪律**，领域工具箱是**专业能力层**。

## 调用方式

1. 在请求里带上：要审的**对象**（文件 / 方案 / PR / 截图的页面）+ 想开的**视角**（或让本包按上表路由）。
2. 本包读取 `references/` 下对应视角的文件，按要求执行。
3. 输出严格遵守上面的「统一评审规则」：分级 + 置信度 + 证据门 + 输出模板。
