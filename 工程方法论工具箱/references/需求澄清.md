# 需求澄清

> 融合自 `obra/superpowers/skills/brainstorming`，并结合 `WorkBuddy 工作原则` 原则一。

## 核心原则

**需求不清楚时，问清楚再动手。猜是最大的浪费。**

动手前多花 1 分钟问清楚，能省下后面 30 分钟返工。

## 什么时候必须先问

- 目标描述笼统（"帮我做个小程序""优化一下这个项目"）
- 存在多种合理解法，且代价差别很大
- 涉及不可逆操作（删除、推送、改写历史、发邮件）
- 用户提到了一个你不确定的专有名词或业务背景

## 提问的方式

**不要问开放式的"你想要什么"**，要给选项：

```
❌ "你想怎么做？"
✅ "两种做法：A 方案改 3 个文件、10 分钟能好但只治标；
    B 方案要重构、1 小时但根治。你选哪个？"
```

规则：
1. **先自己调研**，带着初步判断去问，不要空手问
2. **一次问到位**，把相关问题打包一起问，不要挤牙膏
3. **每个选项说清代价**，而不只是说清好处
4. **给出推荐**并说明理由 —— 用户要的是建议，不是选择题

## 需求澄清清单

动手前确认这五件事：

| 项 | 要确认的内容 |
|---|---|
| **目标** | 做完后什么状态算成功？可衡量吗？ |
| **范围** | 哪些做，哪些明确不做 |
| **约束** | 时间、环境、不能动的东西（如不能 push、不能删文件） |
| **交付物** | 要文件？要报告？要代码？还是只要一个结论？ |
| **验收** | 怎么判断做对了？有测试数据吗？ |

## 遇到「用户自己也不确定」时

- 先用最小成本做一个可看的东西（原型 / 提纲 / 一页纸），让他对着实物提意见
- 人对着具体东西才能说出真实想法，对着空想很难

## 本地化提示

- 用户偏好**中文、表格/要点、关键数字加粗**
- 用户明确要求**拒绝模拟数据**，调研必须基于真实来源（如 GitHub API 实测，不用文章里的二手数字）
- 用户习惯**先给分析和选项，由他决策后再执行**——不要在没确认前就大改
