# 系统化调试

> 融合自 `obra/superpowers/skills/systematic-debugging`。

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

**没走完第一阶段，就不许提出任何修复方案。**

## 什么时候用

任何技术问题：测试失败、运行报错、行为不符预期、性能问题、构建失败、集成问题。

**尤其在这些时候更要用**（越想跳过越不能跳）：
- 时间紧、线上事故 —— 紧急感会诱使你去猜
- 「就改一小行」看起来很明显 —— 明显的问题也有根因
- 你已经试了好几种改法 —— 说明一直没找到根因
- 上一次的修复没生效 —— 说明修的是症状

## 四个阶段（必须按顺序）

### 阶段一：根因调查

在动手改任何东西之前，完成以下四步：

**1. 完整读错误信息**
- 不要跳过错误和警告，它们常常直接包含答案
- 读完整个 stack trace，不要只看最后一行
- 记录：行号、文件路径、错误码
- Windows 下注意：退出码比 stdout 更可靠，用 `echo "exit=$?"`

**2. 稳定复现**
- 能稳定触发吗？具体步骤是什么？每次都发生吗？
- 复现不了 → 继续收集数据，**不要猜**
- 写最小复现脚本（这一步本身就常常暴露根因）

**3. 检查最近的变更**
- 什么改动可能导致这个问题？`git diff`、最近的 commit
- 新增的依赖、配置变更、环境变量
- 环境差异（换机器、换 Python/Node 版本、换工作目录）

**4. 收集证据并追踪数据流**
- 在关键节点打印/记录实际值，而不是凭想象推断
- 顺着数据流往上追，找到第一个出现错误值的位置
- **区分「哪里报错」和「哪里出错」** —— 这两者常常不是同一处

**产出**：一句话说清根因，例如「不是 `nul` 路径解析的问题，是安全描述符拒绝了 DELETE 权限」。
说不出这句话，就退回继续调查。

### 阶段二：模式分析

- 找到问题前，先找到能稳定复现的最小场景
- 对比「正常情况」和「异常情况」的差异点
- 如果之前修过类似问题，看是不是同一个根因的不同表现

### 阶段三：假设与验证

- 基于根因提出**一个**假设（不要一次改一堆地方）
- 设计能**证伪**这个假设的验证，而不是只找支持的证据
- 假设被推翻 → 回到阶段一，用新证据重新分析

### 阶段四：实施修复

- 针对根因修复，不是针对症状
- 补一个能抓住这个 bug 的测试（回归测试）
- 用原始症状复测，确认真的修好了

## 反面清单

| 行为 | 为什么错 |
|---|---|
| 报错就改，改完不报错就当好了 | 症状消失 ≠ 根因消除 |
| 同时改好几个地方 | 不知道哪个起作用，也不知道哪个引入了新问题 |
| 靠重启 / 清缓存"解决" | 没定位根因，一定会复现 |
| 跳过复现直接猜 | 猜对是运气，猜错是常态 |
| 只看最后一行报错 | 根因常常在 stack trace 中间 |

## 本地化提示

- **Windows 权限类问题**：`GetLastError=5` / `0xC0000022` 都是拒绝访问。先分清是「路径解析问题」还是「权限问题」——
  可用句柄级 `SetFileInformationByHandle` 试探：能打开但拿不到 DELETE 权限，就是权限问题，用户态无解，需要管理员。
- **Git Bash 下 Windows 命令**：`del`、`chcp` 等 cmd 内建命令在 Git Bash 里不存在，
  重定向符号可能生成名为 `nul` 的真实文件，排查时留意。
