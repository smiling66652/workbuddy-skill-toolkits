# 测试驱动开发（TDD）

> 融合自 `obra/superpowers/skills/test-driven-development`。

## 铁律

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

先写了代码再补测试？**删掉，从测试重新开始。**

没有例外：
- 不留着当「参考」
- 不边写测试边「适配」它
- 不看它
- 删就是删

## 为什么必须先看它失败

如果你没亲眼看见测试失败，你就不知道这个测试到底在测什么。
先写代码再补测试，测出来的只是「代码现在的行为」，而不是「我们期望的行为」——
这种测试在代码改错时不会报警，等于没有。

## 红绿重构循环

```
RED      先写一个失败的测试        →  运行，确认它失败
   ↓                                    ↓ 失败方式不对 → 重写测试
GREEN    写最少的代码让它通过      →  运行，确认全绿
   ↓                                    ↓ 没过 → 继续改代码（不改测试）
REFACTOR 清理代码，保持全绿        →  每改一步都跑一遍
   ↓
下一个测试
```

要点：
- **RED 阶段要确认「以正确的方式失败」**——失败原因是断言不成立，而不是语法错误或 import 失败
- **GREEN 阶段写「最少」的代码**——不要顺手加功能，不要提前优化
- **REFACTOR 只在全绿时进行**，每步都重跑测试

## 什么时候用

**总是用**：新功能、修 bug、重构、行为变更。

**可以问过用户后跳过**：一次性原型、生成的代码、纯配置文件。

心里冒出「这次就跳过吧」——**那就是该用的时候**。

## 本地化实践

- Python：优先 `pytest`，放在 `tests/` 下，文件名 `test_*.py`
- Node：优先 `node --test`（22.x 内置），无需额外依赖
- Windows 下用受管运行时跑，避免版本差异导致假失败：
  - `C:\Users\Matebook\.workbuddy\binaries\python\versions\3.13.12\python.exe -m pytest tests/ -v`
  - `C:\Users\Matebook\.workbuddy\binaries\node\versions\22.22.2-2\node.exe --test`
- 跑完必须看退出码，不能只看有没有输出

## 与调试的关系

- 修 bug 时：先写一个能复现这个 bug 的**失败测试**，再修 → 修好后测试变绿，且这个 bug 永远不会再回来（回归测试）
- 这正好把「系统化调试」的阶段一（稳定复现）和 TDD 的 RED 阶段合并了
